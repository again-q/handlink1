# 拟真环境：比「能跑通」更接近真机（2026-11-26）

> 一句话：现在这套环境**会失败**——它会卡电流、会排队、会瞬移不了、会顶到桌子、
> 会被别的客户端踢下线。所有「坏」的行为都对着真机实测数据写，
> 并且每一条都有回归测试钉住，退化回去就红。

## 0. 为什么还要再拟真一层

原来的仿真（`bus.SimBus` / `arm.SimArm`）是「记录目标 + 立刻到达」：
没有时间、没有电流、没有队列、没有故障。它保证流程**能跑通**，
但真机上踩过的坑它一个都复现不了，于是同一类问题会在真机上再犯一次。

这一轮的目标是把「真机上咬过人的行为」搬进仿真。判据很直接：
**如果仿真里跑绿了，真机上不该再出现同一类事故。**

## 4. 怎么用

```bash
# 1) 服务 + 虚拟臂：三维视图、使能、组动作全走真协议
python -m handlink serve --sim-arm

# 2) 直接在仿真器上跑脚本（脚本一行都不用改）
python -c "from handlink import armsim, arm; v=armsim.VirtualDobot().start(); a=v.arm(); print(a.check()); v.stop()"

# 3) 抓取流程放到「会卡住」的手上跑

```

`--sim-arm` 会起一个 `VirtualDobot`，把 29999/30004 都绑在系统分配的端口上，
并且**不碰** 192.168.5.1 —— 现场调试时开着真机也不会被它干扰。

## 6. 已知的**真缺陷**（仿真复现出来的，还没修）

### 6.1 抓取互锁会放行「卡住的手」

`handlink/pick.py` 的 `clenched()` 判据是「实际角 ≥ 目标角 × 0.6」。
真机实测：0.6 A 多指同动会触发 I-LIM 卡在 **118°**，而 140° × 0.6 = 84°，
118° 轻松过线 —— 于是互锁放行，臂把一只半开的手抬起来。

仿真里这条能被稳定复现（`tests/test_pick_realistic.py::TestKnownInterlockHole`）：
卡住时停在 118.6° 且 `clenched()` 返回 `True`。同一个测试类里也验证了
替代判据可行：卡住时「最近 1 s 内角度几乎不变」，正常合手时每 0.3 s 涨 >5°。

**修法**（还没动代码，因为这会改变抓取行为，要你确认）：把 `clenched()` 从
「看比例」改成「看比例 **且** 最近 N 毫秒还在动 **且** 心跳没有 I-Lim 位」。

### 6.2 `kin.ik` 对部分工位点位会落进奇异支管

`(400, 0, 300, 180, 0, 0)` 这类「常用演示位姿」实测反解误差可达几百毫米，
但 `SimArm` 会照单全收（真机控制器走 `useJointNear=1` 自己挑支管，
本地数值解没有这个约束）。写测试时用**关节角**或工作空间内闭合的点，别用演示位姿。


## 8. 真机故障复现库：`handlink/faults.py`

不是通用仿真器，是**这个工位真实踩过的 13 个坑**，每个都能一键重放：

```bash
python -m handlink.faults                        # 命令行跑全量，出汇总表
```

```python
from handlink import arm, faults, armsim

a = arm.SimArm(joints=[0, -25, -40, 0, 65, 0]); a.enable()
faults.run("servoj_stop_holds", a)          # 单条
faults.run_all(a)                           # 全量 + 汇总表

sim = armsim.VirtualDobot().start()          # 真 29999 协议，判据最硬
faults.run_all(sim.arm())
```

每个场景返回 `{name, symptom, expected, observed, passed, hint, trace}`：
`observed` 是「这一次到底看到了什么数字」，`trace` 是它每一步做了什么。
出问题先看 `trace`，别猜。

| 场景 | 现象 | 出处 |
| --- | --- | --- |
| `movl_queue_overflow` | 一次 `wait=False` 推 200 条 → 队列满、被拒 | 2026-11-24 真机 |
| `batch_vs_cadence` | 分批等 → 一卡一卡；不分批 → 塞满 | 2026-11-24/25 |
| `servoj_default_t_lag` | ServoJ `t` 默认 0.1 → 朝 100 ms 前的目标走 | 遥操作调研 1.1 |
| `servoj_stop_holds` | 停发后保持、mode=5、不跑位不报警 | 实测（手册没写） |
| `speed_factor_ignores_servo` | 1% 速度因子对 ServoJ 无效 | 手册 p.89 |
| `j6_drift_hits_limit` | 每写一条 300 mm 漂 ~50° → −357.9° 报警 | 毛笔字 2④ |
| `tip_53mm_short` | 指尖比模型长 53 mm，说还有 55 mm 时已贴上 | `cell.py:80-83` |
| `port_29999_preempted` | 29999 被抢占 → 10053 | 毛笔字 2⑦ |
| `error_codes_matter` | −1（状态不允许）vs −10000（指令不存在） | 遥操作调研 1 |
| `joint_limit_rejected` | 关节超限 / 单步 >45° / 段数超上限被拒 | `kin` + `arm_actions` |
| `step_too_big` / `segment_too_long` | 同上，分两层 | `arm_actions.validate` |
| `estop_blocks_motion` | 急停红灯但 `GetErrorID` 全空：不许动、别误报 | `.tmp/fault3.out` |

**退化要明说**：`SimArm` 是应用层助手，没有伺服动力学。这类场景在它身上会
`skipped=True` 或在 `observed` 里写清「缺什么能力」，**不会静默失败**。
要硬判据就用 `VirtualDobot`——同一批场景在它身上必须真的 `passed=True`。

### 这些场景自己撞出来的判断

- `movl_queue_overflow` 的修法不是「分 N 条一批、等这批走完」（那会变成一卡一卡），
  而是**按算法队列在途条数做窗口节流**（`service.arm_trace` 的 `window`）。
- `SimArm.current_cmd_id()` 会随队列推进**回退**（报的是正在执行那条的 id），
  真机 ID 单调递增。节流里必须取 `max`，否则积压算成负数。
- `estop` 与 `servo_alarm` 必须分开：前者 `GetErrorID()` 可能是全空的，
  看 `SafetyState` / 安全链，不要一直去 `ClearError()`。

## 9. 一键自检：`scripts/sim_report.py`

把所有「仿真实测 vs 真机实测」的关键数字打一张表，不需要任何硬件：

```bash
python scripts/sim_report.py          # 人看
python scripts/sim_report.py --json   # 给 CI / 别的程序吃
```

2026-11-26 本机输出（数字会随机器小幅浮动，看数量级）：

```
项目                     仿真             真机实测
------------------------------------------------------
29999 GetPose 中位       4.63 ms        3.9 ms
29999 GetPose max        5.65 ms        5.4 ms
ServoJ ACK 中位          6.93 ms        6.2 ms
ServoJ ACK p90           8.01 ms        7.3 ms
手 90 度行程             1.58 s         1.60 s
0.6 A 卡住角度           118.6 deg      118 deg
六指心跳                 3000 fps       3000 fps
------------------------------------------------------
40 度关节行程（虚拟时钟） 0.80 s          —
同段的墙钟耗时           0.4 ms          —
```

注意最后两行：**仿真里「走 40° 要 0.8 秒」这件事发生在虚拟时钟上，墙钟只花 0.4 ms**。
这就是为什么 `SimArm` 可以既真又快——要真按墙钟走，`faults` 那 13 个场景得跑十几分钟。
需要真时序时用 `SimArm(realtime=True)` 或 `VirtualDobot`。

| --- | --- | --- |

### ② 这次是真抓到的一条

写这一节的时候顺手试了一下，虚拟控制器原来**放行** `r=3.0`——但真机实测是 `-50001`。
也就是说，`arm.movl_r()` 里那句「必须 `floor(x+0.5)` 不能 `round()`」的修法，
在仿真里其实**从来没被验证过**，写错了也不会红。现在补上了，
并且加了 `test_movl_r_never_sends_a_float` 从链路上兜一层。

### ④ 那条最有价值的反而复现不了

J6 累积漂移是这批坑里最凶的（-357.9° 整台臂报警）。仿真里它**不会重现**：

```
连续 20 条 300 mm 横线，J6 序列：
24.2, 55.0, 68.6, 67.7, 66.6, ... 44.9, 39.9, 32.8, 22.2
净漂移 -2.0 度（真机是每条 +50 左右单向爬）
```

原因是真机的累积来自「控制器自己挑 IK 支管，挑完就记住」，而虚拟控制器每帧
独立解、按种子选。要复现得给控制器加「支管记忆」，但那等于我自己拍一个真机
行为出来——没有实测数据支撑，宁可不做。**所以防缠逻辑目前只能靠规划层单测兜。**

回归：`tests/test_trace_quirks.py`（8 条）。

## 7. 边界：仿真不负责的事

- **力学**：抓取力、接触、摩擦、物体掉落都没建模。手是「会卡」但不是「会滑」。
- **视觉/标定误差**：`scene.py` 的像素→基座换算仍然理想。
- **多机协同时序**：只模拟单臂单手的抢占，没模拟两台客户端互踢的时序竞争。
- **温度漂移**：电机温度只出数值，不影响性能。

要做这几样，得先有对应的真机实测数据，否则又是一轮「拍脑袋仿真」。
