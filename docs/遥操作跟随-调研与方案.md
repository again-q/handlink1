# 机械臂「跟手」调研与方案（2026-11-25）

> 目标：人手在空间里动，机械臂末端实时跟上；**位置 + 手腕朝向都跟**；要快、要顺、要安全。
> 不要求跟踪小臂/大臂，不要求力反馈。
>
> 这份文档是**调研 + 真机实测**的结论，不含新代码。标注约定：
> 【实测】本机今天量到的；【手册】厂家文档原文；【文献】公开资料；【推断】我的判断。

---

## 0. 结论先行

1. **下发这一半已经不是问题了。** 今天在真机上打通了 `ServoJ`：29999 口、30 ms 节拍、
   ACK 中位 **6.2 ms**、60/60 全接受、原地保持**零漂移**；停发 10 s 也不报警、不跑位。
   以前「逐条 MovL 卡死/一卡一卡」的矛盾，换接口就没了，不用调参。
2. **感知这一半是真正的瓶颈，而且缺的是「位置」。** 手套（MotionVenus = 孚心 FOHEART
   HMax）的 `x/y/z` 不是世界位置——官方定义是「胯部固定在原点」的骨架自洽值，
   手的整体平移从来没有被任何传感器观测到。**朝向已经有了，位置还没有。**
3. **软件能补一部分，但补不出可靠的深度。** 单目相机能把「平面内位置」补到 ±5~10 mm、
   延迟 ~10 ms（本机实测 MediaPipe 单帧 9.7 ms），但 z 只能靠手的大小猜，误差 10~30%。
   真要 3D，最便宜的不是买设备，是**把已经有的奥比 Gemini 336L 深度相机插回来**。
4. **买设备的正确理由是「抗遮挡 / 抗光照 / 精度」**，不是「能不能跟」。腕上挂一个
   Vive Tracker（≈ ¥1940）是厂商原生支持的组合（MotionVenus 设备属性里就有
   「参考 HTC Tracker」），位置 mm~cm 级，2~4 天能跑。
5. **安全网不能指望 SpeedFactor**：手册写明 ServoJ/ServoP **不受全局速率影响**
   （p.89），唯一可靠的是软件逐帧限幅 + 看门狗 + deadman。

## 1. 今天在真机上量到的（Nova 5，192.168.5.1）

| 项目 | 结果 | 说明 |
| --- | --- | --- |
| 29999 往返延迟 | 中位 **3.9 ms**、p90 5.0、max 5.4 | 连续 30 次 `GetPose()`，文本一问一答 |
| `ServoJ` 是否支持 | **支持** | 回复 `0,{ResultID},ServoJ(...);`；未知指令回 `-10000`，能区分 |
| ServoJ ACK 延迟 | 中位 **6.2 ms**、p90 7.3、max 12.0 | 60 帧 @30 ms 节拍，全部 `ErrorID=0` |
| 原地保持精度 | 关节漂移 **0.000°**、位姿漂移 **0.0 mm** | 目标 = 当前关节角，连续 60 帧 |
| **停发之后** | 保持最后目标，`RobotMode=5`，`ErrorStatus=0`，10 s 内不跑位、不报警 | 手册没写这件事，实测补上 |
| `30003` 端口 | **不监听**（连接超时） | CR 系列文档的「30003 运动口」在 Nova 上不成立，ServoJ 走 29999 |
| `SpeedFactor` | **对 ServoJ/ServoP 无效**（【手册】p.89「该指令不受全局速率影响」） | 速度因子只管 MovJ/MovL/MoveJog |
| 未使能时发 ServoJ | 回 `-1`（状态不允许），不是「指令不存在」 | 可用它做上线自检 |
| 臂的当前状态 | 测试前 `mode=4`（下使能）、位姿 (441.3, −199.7, 923.7)；**测试后已恢复成 mode=4** | 我做的只有「使能 → 保持 → 下使能」 |

> 结论：30 ms 节拍 + 4~12 ms ACK，**时间预算够**，剩下的延迟全在控制器插补和机械臂本身。

### 1.1 ServoJ / ServoP 的用法（【手册】V4.6.0 第 89–91 页）

```
ServoJ(J1,J2,J3,J4,J5,J6, t=.., aheadtime=.., gain=..)
ServoP(X,Y,Z,Rx,Ry,Rz,     t=.., aheadtime=.., gain=..)
```

- 官方建议 **33 Hz**，即每 **30 ms** 发一次；
- `t`：这一段走多久，[0.004, 3600] s，默认 **0.1**。**默认值太大**——控制器会一直朝
  「100 ms 前的目标」慢慢挪，等效一阶低通，很容易被误判成网络慢。首测用 **0.03**；
- `aheadtime`：类 D 项，[20,100]，默认 50；`gain`：类 P 项，[200,1000]，默认 500；
- 手册只说了「受速度限制约束、步长太大时会跟不上」，**没写**丢帧/超时/报警行为；
- 唯一的退出方式是停发（实测会保持）或 `Stop()`；**V4.6.0 全文没有 `Sync()`**。

### 1.2 还没验证、但必须先验证的一件事

`ServoJ` 在手册里被归为**队列指令**（p.79），但它的语义又要求 33 Hz 连续覆盖。
这两件事是矛盾的：如果控制器严格 FIFO，30 ms 一发会**积压成橡皮筋**（手停了臂还在走）。

【推断】实际大概率是「每个控制周期取最新一帧」（latest-wins）。验证方法：

1. 30 ms 流里发一个 5° 的阶跃，同时用 30004 读 `QActual`，量「发出去 → 动起来」的真实滞后；
2. 对比 `CurrentCommandId` 和自己收到的 `ResultID`：差值持续变大 = 在排队；
3. 若确实排队：改成单帧在途（收到 ACK 再发下一帧）+ 陈旧帧丢弃。

**这件事没验之前，不要接人的手。**

## 2. 感知：位置从哪来

### 2.1 手套单独为什么不行（【文献】孚心官方文档）

- MotionVenus 是**孚心科技 FOHEART** 的软件，手套是 HMax 系列；UDP 帧是
  `pos + euler`，每关节 6 个数——仓库里 `glove.py` 收到的正是这个格式。
- 官方对 `pos` 的定义确实是「全局坐标系、单位 m」，**但这个「全局系」的根节点钉死在胯部**：
  官方原话「此模式将胯部固定在原点……人体骨骼可以自由动作但是胯部保持在原点」。
- 所以 `x/y/z` 是用**固定骨长 + IMU 姿态**正推出来的骨架自洽值：手一挥，手背的 x/y/z 不动。
- 纯 IMU 推位置靠二次积分：零偏 0.1 mg → 1 s 偏 5 mm、10 s 偏 0.49 m；姿态差 1° 就凭空
  产生 ~17 mg 的假加速度。**任何价位的纯 IMU 都不成立。**
- 官方给的解法也是现成的：腕上加 **HTC Tracker**（「参考 HTC Tracker」模式），或接它家
  光学动捕做 EKF 融合（MotionUranus 文档里直接写「腕部漂移 → 用光学数据定期重置腕部坐标系」）。

【推断，建议现场 5 分钟验一下】手不戴手套整体前移 50 cm，看右手第 0 节 x/y/z 变不变；
预期几乎不变，这就能当场证明「位置不能用」。

### 2.3 「软件能不能弥补」

能补一部分，按性价比排：

1. **平面内位置**：MediaPipe 手腕点 + 单应，本机实测单帧 **9.7 ms**（640×360），
   30 Hz 很轻松；精度 ±5~10 mm。
2. **相对位移（更顺）**：对掌心做 LK 光流，只取**帧间增量**，亚像素级、比逐帧检测平滑得多；
   正好匹配你要的「相对位置」。缺点是会漂，靠 clutch（松手重按）重置。
3. **深度（z）**：单目只能靠「手在画面里多大」反推，**误差 10~30%，快速挥手必糊**；
   加桌面平面约束能救「贴着桌面」的场景，救不了「手举高」。
4. **真 3D**：只有深度相机或 Tracker 能给。深度相机你们已经有——**这是 0 元的正解**，
   不是买设备。

一句话：**软件能把「左右上下」补到能演示，补不出可靠的「远近」；要真 3D 先插深度相机。**

## 3. 控制回路怎么搭

```
传感器(30~110Hz) ──► 映射/滤波 ──► 最新值邮箱(覆盖,不排队) ──► 33Hz 定时器 ──► ServoP/ServoJ
      │                    │                                      │
      └─ 时间戳 ───────────┘                                      └─ 30004 反馈核对
```

- **只发最新**：邮箱里永远只有一格，新的覆盖旧的；超过 100 ms 的帧直接丢（陈旧帧是
  「橡皮筋」的根源）。
- **映射**：`R = R₀ · (H₀⁻¹ · H)`，`H₀/R₀` 是按下 clutch 那一刻的手位姿和末端位姿。
  这样**完全不需要手眼标定**——未知的坐标变换在两端同时被消掉。松开 clutch 就冻结，
  再按一次重新取原点（手可以回到舒服的位置）。
- **缩放**：1.0 起步；演示 1.2 足够，**不要 >2**（等比例放大抖动）。
- **姿态**：必须四元数 + 短弧误差；欧拉角直传会在 ±180° 附近跳变（我今天在
  `kin.ik` 上就撞到这个问题：`roll=±180` 的位姿解不出来，`roll=0` 的解得很好）。
- **滤波**：One-Euro（位置 min_cutoff ≈1.5 Hz、beta ≈0.02，速度项）；死区 1 mm / 0.3°。
- **限幅**：每帧 ≤ 25 mm / 4°；单帧 >50 mm 且方向突变 → 判为跳变，暂停并要求重新 clutch。
- **看门狗**：>100 ms 没有新目标 → 停止发新目标（控制器会保持最后位置，实测）。
- **边界**：进入软边界 50 mm 内余弦减速，越界只钳制那一根轴，**不要回弹**
  （14 kg 的臂反向弹一下是安全隐患）。

### 3.1 用 ServoP 还是 ServoJ

| | ServoP（笛卡尔） | ServoJ（关节） |
| --- | --- | --- |
| 逆解 | 控制器内部做 | 要本地 IK |
| 代码量 | 很小（直接发位姿） | 要 `_ik_once` + 热启动 + 防跳支 |
| 风险 | 控制器内部 IK 可能**跳配置**（腕部翻转） | 自己能控，但要处理奇异点 |
| 本机可行性 | ✅ 已实测接受 | ✅ 已实测接受 |

**建议：第一版用 ServoP**（位置 + 姿态直接发，一个函数就能跑通）；等手感对了，再换
ServoJ + 本地阻尼 IK 去治腕部翻转和 J4/J6 拧线。

> 注意：`kin.ik()`（多种子版）实测 **243 ms/次**，绝对不能进实时回路；
> 要进回路只能用 `_ik_once` + 上一帧热启动（目标很近时约 0.09 ms）。

### 3.2 安全网（必须自己写）

因为 `SpeedFactor` 对 ServoJ/ServoP 无效：

1. deadman：按住才发，松开立即停发；
2. 逐帧限幅（关节 ≤1°/帧、笛卡尔 ≤2~5 mm/帧）；
3. 工作空间包围盒（x/y/z 硬边界）；
4. 看门狗（>100 ms 无新帧）；
5. 异常即 `Stop()` + 下使能；
6. 人机距离：演示时观众 ≥1.5 m，操作员手不离急停。

## 4. 延迟预算（33 Hz 下发，不含视频）

| 环节 | 深度相机方案 | Tracker 方案 | 依据 |
| --- | --- | --- | --- |
| 采集 | 33 ms | 10–11 ms | 30 Hz vs 90–100 Hz【文献】 |
| 推理（MediaPipe） | 10 ms | — | **本机实测 9.7 ms** |
| 传输/解析 | 2 ms | 2 ms | 本机回环【推断】 |
| 滤波 | 10 ms | 10 ms | One-Euro【推断】 |
| 映射/限幅 | <1 ms | <1 ms | 纯浮点 |
| 下发 ACK | 6 ms | 6 ms | **本机实测 6.2 ms** |
| 控制器插补 | ~38 ms | ~38 ms | 3 × t + lookahead【推断】 |
| 机械伺服 | 15 ms | 15 ms | 【推断】 |
| **合计** | **~115 ms** | **~90 ms** | |

- 人对手感「跟手」的容忍大约 100 ms；Tracker 方案正好卡在线上，深度相机方案略超。
- **最大的一项是控制器插补**，所以把 `t` 从 0.1 调到 0.03 比优化网络有用得多。
- 60 Hz 下发能否吃住**必须实测**（控制器推荐就是 33 Hz，发太快可能只是把点堆在队列里）。

| 天 | 做什么 | 验收 |
| --- | --- | --- |
| D1 | `arm.py` 加 `servo_p/servo_j`（不等待、不阻塞、ACL 短超时）；`arm_servo.py` 做 33 Hz 邮箱 + 限幅 + 看门狗；先用**假手位姿**（正弦驱动的虚拟点）跑 | 臂跟着虚拟点平滑走完一个 20 cm 圆，无卡顿，`ResultID` 不积压 |
